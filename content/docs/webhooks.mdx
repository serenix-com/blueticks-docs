Webhooks push Blueticks events to your server over HTTPS, in near real time — so
you can react to message delivery, incoming WhatsApp messages, group activity,
session changes, and campaign progress **without polling the API**.

This guide assumes you have an API key ([Authentication](/docs/authentication))
and an SDK client set up ([Quickstart](/docs/quickstart)).

## 1. Register a webhook

Point an HTTPS endpoint at Blueticks and subscribe it to the events you care
about (pick any from the [catalog](#3-events-you-can-subscribe-to) below). You
can register several endpoints, each with its own event list.

**Settings → API → Webhooks**.

Three optional settings narrow and secure a webhook. Each has its own section
below: [`chat_ids`](#7-filter-by-chat) and `include_status_and_channels` pick
which chats you hear about, [`POST /v1/webhooks/{id}/test`](#8-send-a-test-event)
checks the endpoint before real traffic, and [`headers`](#9-send-custom-headers)
adds your own `Authorization` or `X-*` headers to every delivery.

## 2. What you receive

Each event is a single HTTPS `POST`. The body is always the same envelope —
only `type` and `data` change:

```json
{
  "id": "evt_01h7za9c8m...",
  "type": "message.delivered",
  "created_at": "2026-04-23T16:42:00.000Z",
  "data": { /* fields specific to this event type */ }
}
```

with these headers:

```
Content-Type: application/json
Blueticks-Webhook-Id: 6a380a8258bece30b485036e
```

- **`id`** is unique per delivery — store it and ignore repeats, since a retry
  can re-deliver an event your server already handled (see
  [Reliability](#5-reliability-retries--auto-disable)).
- **`idempotency_key`** (optional) identifies the underlying occurrence, not the
  delivery. Today only `poll_vote_webhook` carries one: the same vote gets the
  same key however many times or from however many engines it is delivered. The
  key is also sent as the `Blueticks-Idempotency-Key` header. Events without one,
  and a poll vote missing its poll id, voter or timestamp, have no such field and
  no header.
- **`Blueticks-Webhook-Id`** is the id of *your* webhook that matched — handy
  when one server backs several endpoints.
- **Respond `2xx` within 10 seconds.** Anything else (or a timeout) is treated
  as a failure and retried. Do heavy work *after* you respond.

## 3. Events you can subscribe to

You only receive the events you subscribe to. Group them however you like across
one or more endpoints.

The fields in each event's `data` are listed in the [webhook event reference](/docs/webhook-events). No public URL to receive webhooks? See [Realtime messages (MQTT)](/docs/realtime).

**Message delivery** — lifecycle of messages *you* send:
`message.queued` · `message.sending` · `message.delivered` · `message.read` · `message.failed`

**Incoming WhatsApp activity:**
- `new_message_received_webhook` — someone messaged you
- `new_message_received_from_me_webhook` — a message sent from your own account. Opt-in: `new_message_received_webhook` stays inbound-only, so subscribe to this one explicitly if you want your own messages too. Same payload shape.
- `reply_to_my_message_webhook` — a reply to one of your messages
- `message_edited_webhook` · `message_deleted_revoked_webhook` — a message was edited / deleted
- `message_reaction_webhook` — an emoji reaction
- `poll_vote_webhook` — a vote on your poll
- `ack_changed_webhook` — a message's delivered/read status changed

**Group &amp; chat activity:**
- `participant_joined_via_link_webhook` · `participant_added_by_admin_webhook` · `participant_left_group_webhook` · `participant_kicked_from_group_webhook`
- `group_admin_changed_webhook` · `group_name_changed_webhook` · `group_description_changed_webhook` · `group_message_pinned_webhook`

**Sessions** — `session.connected` · `session.disconnected`

**Campaigns** — `campaign.started` · `campaign.paused` · `campaign.resumed` · `campaign.completed` · `campaign.aborted`

The [Create webhook reference](/docs/api/webhooks/create-webhook) lists the exact
accepted enum.

## 4. Verify requests really came from Blueticks

Every webhook gets its own **signing secret** (`whsec_…`). It is returned as
`signingSecret` in the webhook object when you create it, and on every
list / get afterwards — store it on your server like any other credential.

Each delivery from a signed webhook carries three extra headers:

```
Blueticks-Webhook-Timestamp: 1776962520
Blueticks-Webhook-Signature: v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
X-Blueticks-Signature: sha256=0b4fa9c2e1d7...
```

- **`Blueticks-Webhook-Timestamp`** — when the delivery was signed, in Unix
  **seconds**.
- **`Blueticks-Webhook-Signature`** — `v1=` followed by the hex
  HMAC-SHA256 of the string `{timestamp}.{raw body}`, keyed with your signing
  secret (the whole string, including the `whsec_` prefix). Because the
  timestamp is signed too, this is the one to use: check the signature *and*
  reject timestamps that are too old to stop replays.
- **`X-Blueticks-Signature`** — `sha256=` followed by the hex HMAC-SHA256 of
  the raw body alone, same key. Simpler, but gives no replay protection.

<Callout type="warn">
Compute the HMAC over the **raw request bytes**, exactly as received — before
any JSON parsing. Re-serializing a parsed object changes key order or
whitespace and the signature will never match.
</Callout>

<Tabs groupId="sdk" persist items={['Python', 'Node.js']}>
  <Tab value="Python">

```python
import hashlib, hmac, os, time
from flask import Flask, request, abort

app = Flask(__name__)
SECRET = os.environ["BLUETICKS_WEBHOOK_SECRET"]  # whsec_...
TOLERANCE_SECONDS = 300

@app.post("/bt-webhooks")
def bt_webhook():
    raw = request.get_data()  # raw bytes, before any JSON parsing
    ts = request.headers.get("Blueticks-Webhook-Timestamp", "")
    sig = request.headers.get("Blueticks-Webhook-Signature", "")
    if not ts.isdigit() or abs(time.time() - int(ts)) > TOLERANCE_SECONDS:
        abort(400)
    expected = "v1=" + hmac.new(
        SECRET.encode(), ts.encode() + b"." + raw, hashlib.sha256
    ).hexdigest()
    if not hmac.compare_digest(expected, sig):
        abort(401)
    event = request.get_json()
    # ... handle event["type"] / event["data"], then respond fast
    return "", 204
```

  </Tab>
  <Tab value="Node.js">

```ts
import crypto from 'node:crypto';
import express from 'express';

const app = express();
const SECRET = process.env.BLUETICKS_WEBHOOK_SECRET!; // whsec_...
const TOLERANCE_SECONDS = 300;

// express.raw keeps the body as a Buffer — do NOT use express.json() here.
app.post('/bt-webhooks', express.raw({ type: 'application/json' }), (req, res) => {
  const raw: Buffer = req.body;
  const ts = req.header('Blueticks-Webhook-Timestamp') ?? '';
  const sig = req.header('Blueticks-Webhook-Signature') ?? '';
  if (!/^\d+$/.test(ts) || Math.abs(Date.now() / 1000 - Number(ts)) > TOLERANCE_SECONDS) {
    return res.sendStatus(400);
  }
  const expected =
    'v1=' +
    crypto
      .createHmac('sha256', SECRET)
      .update(Buffer.concat([Buffer.from(`${ts}.`, 'utf8'), raw]))
      .digest('hex');
  const a = Buffer.from(expected);
  const b = Buffer.from(sig);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    return res.sendStatus(401);
  }
  const event = JSON.parse(raw.toString('utf8'));
  // ... handle event.type / event.data, then respond fast
  res.sendStatus(204);
});
```

  </Tab>
</Tabs>

To use `X-Blueticks-Signature` instead, drop the timestamp: compare
`sha256=` + HMAC-SHA256(secret, raw body) against the header.

**Webhooks created before signing shipped stay unsigned** — they have no
`signingSecret` and their deliveries carry none of the headers above. Delete and
recreate such a webhook to get a secret. Until then (or if your platform can't
compute an HMAC), you can still protect an endpoint by registering a URL that
contains a hard-to-guess token, e.g.
`https://api.your-server.com/bt-webhooks?token=ek3f9q2...`, and rejecting any
POST without it. Always serve the endpoint over HTTPS. You can also have Blueticks send your own
`Authorization` header with every delivery, see
[Send custom headers](#9-send-custom-headers).

## 5. Reliability: retries &amp; auto-disable

- Each delivery attempt must complete within **10 seconds**.
- A non-2xx response or a timeout is retried — up to **8 attempts total** (the
  first delivery plus 7 retries) over roughly **21 hours**, with growing backoff
  between attempts: `1m → 5m → 15m → 1h → 2h → 6h → 12h`.
- Because of retries, the **same event can arrive more than once** — dedupe on
  the delivery `id`. For poll votes, dedupe on `idempotency_key` instead: an
  account connected through more than one engine can send you the same vote as two
  deliveries with different `id`s.
- An endpoint that keeps failing is backed off, not hit with every event. It
  **auto-disables** once it has failed continuously for **3 days** with at
  least **10** failed attempts. Once your server is healthy, re-enable it by
  patching `status: "enabled"` (next section).

## 7. Filter by chat

By default a webhook receives every matching event from every chat. To hear
about only some chats, set `chat_ids` when you create the webhook or `PATCH` it
later:

```bash
curl -X POST https://api.blueticks.co/v1/webhooks \
  -H "Authorization: Bearer BLUETICKS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://api.your-server.com/bt-webhooks",
    "events": ["new_message_received_webhook"],
    "description": "Support group only",
    "chat_ids": ["120363025246125486@g.us"],
    "include_status_and_channels": false
  }'
```

- **`chat_ids`** is up to 100 chat ids, each 3 to 128 characters. Omit it, or
  send `[]`, to receive every chat. On `PATCH`, `[]` clears an existing filter.
  Repeated ids are collapsed.
- An event is delivered when its chat is in the list. Events that are not tied
  to a chat (`session.*`, `campaign.*`) always pass the filter.
- `@c.us` and `@s.whatsapp.net` are treated as the same person. A phone id
  (`@c.us`) does **not** match a chat that WhatsApp delivers as `@lid`. If a
  contact can arrive in either form, list both ids.
- **`include_status_and_channels`** defaults to `true`. Set it to `false` to
  skip WhatsApp Status (`status@broadcast`) and Channel (`@newsletter`) events.
  It combines with `chat_ids`: an event must pass both.

The webhook object returns both settings on every read:

```json
{
  "success": true,
  "data": {
    "id": "6a380a8258bece30b485036e",
    "url": "https://api.your-server.com/bt-webhooks",
    "events": ["new_message_received_webhook"],
    "description": "Support group only",
    "status": "enabled",
    "chat_ids": ["120363025246125486@g.us"],
    "include_status_and_channels": false,
    "header_names": [],
    "createdAt": "2026-11-18T19:04:00.000Z",
    "signingSecret": "whsec_..."
  }
}
```

Webhooks created before these settings existed return `chat_ids: []` and
`include_status_and_channels: true`, so they keep receiving everything.

## 8. Send a test event

`POST /v1/webhooks/{id}/test` sends one signed sample event to the webhook's
URL and tells you what happened, so you can check your endpoint and signature
code before real traffic arrives. It needs the `webhooks:write` scope.

```bash
curl -X POST https://api.blueticks.co/v1/webhooks/6a380a8258bece30b485036e/test \
  -H "Authorization: Bearer BLUETICKS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"event": "new_message_received_webhook"}'
```

The body is optional. `event` must be one the webhook is subscribed to, and
defaults to the first one. Otherwise the call returns `400`.

```json
{
  "success": true,
  "data": {
    "ok": true,
    "status": 204,
    "latency_ms": 142,
    "event": "new_message_received_webhook"
  }
}
```

The call returns `200` even when your endpoint fails; check `data.ok`. When it
fails, `data.hint` says what to fix (a 4xx or 5xx status, a timeout, a DNS or
TLS error, a redirect, or a URL that resolves to a private address). Fields
that have no value, such as `status` after a timeout, are omitted:

```json
{
  "success": true,
  "data": {
    "ok": false,
    "latency_ms": 10003,
    "event": "new_message_received_webhook",
    "hint": "Timed out after 10s. The endpoint must answer within 10 seconds; acknowledge first, process later."
  }
}
```

What the endpoint receives is the normal envelope with two differences: the
`id` starts with `evt_test_`, and the body carries `"test": true`. For an
incoming-message event the `data` is a sample message; for `message.*`,
`session.*` and `campaign.*` events it is a short note, not real data. Your
[custom headers](#9-send-custom-headers) and the signature headers are sent
exactly as on a real delivery, so signature verification can be tested too.

A test goes straight to your endpoint. It is not queued or retried, it is not
recorded as a delivery, and it never counts toward
[auto-disable](#5-reliability-retries--auto-disable). The response body of your
endpoint is not returned, and redirects are not followed. Limits: one test per
webhook every 5 seconds, and 20 tests per hour per account (`429` beyond that).

## 9. Send custom headers

Set `headers` to add your own headers to every delivery, typically an
`Authorization` token so your receiver can reject anything else:

{/* validate:ignore unknown-field — headers is a free-form name/value map (additionalProperties), so its keys are not in the schema */}

```bash
curl -X PATCH https://api.blueticks.co/v1/webhooks/6a380a8258bece30b485036e \
  -H "Authorization: Bearer BLUETICKS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"headers": {"Authorization": "Bearer 7f3c9a1e5b2d4c68", "X-Source": "blueticks"}}'
```

- Allowed names: `Authorization`, or a name that starts with `X-`. `X-Blueticks-*`
  and `X-Forwarded-*` are rejected, as is any other name. Names are
  case-insensitive and may not repeat.
- Up to 10 headers. Each value is 1 to 1024 printable ASCII characters, with no
  line breaks. A bad header returns `400` and names the offending header.
- **Values are sealed.** They are stored encrypted and never returned. A read
  shows only the names:

  ```json
  "header_names": ["Authorization", "X-Source"]
  ```

- **System headers win.** `Content-Type`, `Blueticks-Webhook-Id`, the signature
  headers and `Blueticks-Idempotency-Key` are always set by Blueticks. A custom
  header with the same name, in any letter case, is dropped.
- `PATCH` **replaces the whole set**: send every header you want to keep. Send
  `"headers": null` (or `{}`) to remove them all. Omit `headers` to leave them
  untouched.

Custom headers are not a substitute for [signature
verification](#4-verify-requests-really-came-from-blueticks). The signature
proves a request came from Blueticks and was not altered; a header only proves
the sender knew your token.
