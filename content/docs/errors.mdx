All error responses use a single envelope shape, regardless of endpoint
or status code. `success` is always `false`, and the details live under `error`:

```json
{
  "success": false,
  "error": {
    "code": "authentication_required",
    "message": "API key required or invalid.",
    "request_id": "req_1a2b3c4d5e"
  }
}
```

## Status codes

| Code | Meaning | Retry? |
|------|---------|--------|
| `400` | Bad request — payload shape is invalid | No |
| `401` | Authentication required — missing / invalid key | No |
| `403` | Permission denied — key lacks required scope | No |
| `404` | Not found — resource doesn't exist or isn't visible | No |
| `409` | Conflict — e.g. an `Idempotency-Key` reused with a different body | No |
| `422` | Unprocessable entity — semantically invalid | No |
| `413` | Payload too large | No |
| `429` | Rate limited — honor `Retry-After` header. On the free plan this is the plan quota, see [Free plan limit](#free-plan-limit) | Yes, after the wait |
| `5xx` | Server error | Yes, with exponential backoff |

## Error codes

Current error codes:

- `authentication_required`
- `permission_denied`
- `not_found`
- `invalid_request`
- `rate_limited`
- `payload_too_large` (`413`)
- `internal_error`

A few conflicts and outages carry their own code:

- `no_engine_connected` (`503`): none of your WhatsApp numbers is connected. The response sets `Retry-After: 30`.
- `idempotency_in_flight` (`409`): an earlier attempt of this send, with the same `Idempotency-Key`, is still in flight and nothing was sent. Retry the same request after `Retry-After`.
- `send_in_flight` (`409`): the same, for an identical message to the same chat sent without a key.
- `AMBIGUOUS_NUMBER` (`409`): several of your WhatsApp numbers have this chat or object. `error.candidates` lists them as `{ numberId, phoneNumber }`; repeat the request naming one with `numberId` or `phone`.

The SDK maps each code to a typed exception class so you can
`catch (RateLimitError)` vs `catch (AuthenticationError)` without
string-matching.

### Validation details

When a request body fails validation (`400`/`422`), the envelope carries
an additional `error.details` array with one entry per offending field:

```json
{
  "success": false,
  "error": {
    "code": "invalid_request",
    "message": "Request body failed validation.",
    "request_id": "req_1a2b3c4d5e",
    "details": [
      { "path": "pollOptions", "code": "too_small", "message": "Array must contain at least 2 element(s)" }
    ]
  }
}
```

## Retry guidance

The official SDKs retry automatically on `429`, `502`, `503`, `504`, and
network errors. Defaults:

- **Base delay:** 500 ms, doubling each attempt, capped at 8 s.
- **Jitter:** random fraction of the current backoff window.
- **Max retries:** 2 (3 total attempts).
- **POST idempotency:** POST without an `Idempotency-Key` header is
  **not retried** on HTTP errors (only on network failures). Supply
  `Idempotency-Key: <your-uuid>` to opt in.

### Retry-After

On `429`, the server returns a `Retry-After` header (seconds or
HTTP-date). The SDK waits that long before the next attempt. On other
retryable statuses, the SDK uses its own exponential backoff.

## Free plan limit

On the free plan the REST API and the MCP server share one quota of **5
requests per 6-hour window**, and any paid plan is unlimited. Past the quota the
API answers `429 rate_limited` with `Retry-After` set to the seconds left in the
window, and an `error.upgrade` object:

```json
{
  "success": false,
  "error": {
    "code": "rate_limited",
    "message": "...",
    "upgrade": {
      "url": "...",
      "text": "...",
      "reset_time": "...",
      "seconds_remaining": 12345,
      "plan": "..."
    }
  }
}
```

Retrying before the window resets fails the same way, so wait `Retry-After`
rather than backing off. The `upgrade.url` field is where to send a person to
lift the limit.

## Per-key rate limits

Separate from the free plan quota, every API key also has short per-minute
limits that apply on **every plan**, paid included. For example,
`POST /v1/scheduled-messages/{chatId}` allows 60 requests per minute per key,
and `GET /v1/scheduled-messages/{id}` allows 600. Past a limit the API answers
`429` with `Retry-After` (seconds until the minute window resets) plus
`X-RateLimit-Limit` and `X-RateLimit-Remaining` headers. Wait `Retry-After`,
then retry.

## Request IDs

Every response (success or error) includes a `X-Request-Id` header.
Error envelopes echo it in `error.request_id` for convenience. Include
request IDs in any support inquiry.

## Example: handle 429 manually

<Tabs groupId="sdk" persist items={['Python', 'Node.js', 'PHP', 'Ruby', 'Go']}>
  <Tab value="Python">

```python
from blueticks import Blueticks, RateLimitError

client = Blueticks()
try:
    account = client.account.retrieve()
except RateLimitError as e:
    print(f"throttled, retry after {e.retry_after}s")
```

```typescript
import { Blueticks, RateLimitError } from "blueticks";

const client = new Blueticks();
try {
  const account = await client.account.retrieve();
} catch (err) {

    console.log(`throttled, retry after ${err.retryAfter}s`);
  }
}
```

```go
import (
	"context"
	"errors"
	"fmt"

	blueticks "github.com/serenix-com/blueticks-go"
)

c, _ := blueticks.NewClient()
_, err := c.Account.Retrieve(context.Background())
var apiErr *blueticks.APIError
if errors.Is(err, blueticks.ErrRateLimit) && errors.As(err, &apiErr) {
	fmt.Printf("throttled, retry after %.0fs\n", apiErr.RetryAfter)
}
```
